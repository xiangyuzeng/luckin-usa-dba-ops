## Join key & linkage (⚠️#1 — resolved empirically; PART 3 caught an initial wrong assumption)

The assignment table `t_user_traffic_distribution` exposes **only `user_no`** (no `uuid`/`device_id_hash` column — confirmed in both RDS and Doris `meta_column`). But the **ID spaces differ**:

| Field | Format | Identity |
|-------|--------|----------|
| `t_user_traffic_distribution.user_no` | 18-digit `111…` | **device_id_hash** (experiment buckets by DEVICE, pre-login) |
| `t_device_history.device_id_hash` | 18-digit `111…` | device hash |
| `t_device_history.user_no` | 13-digit | member id |
| `t_order.user_no` | 13-digit | member id |

→ Correct linkage = ⚠️#1's **first branch**: `assignment.user_no = device_history.device_id_hash`, then `device_history.user_no` (member) = `t_order.user_no`. `t_device_history` is the **device→member bridge**.
A first attempt joining `user_no=user_no` returned **0 orders / 0 device matches** on the 3-day slice; PART 3 caught it and the ID-format sampling corrected it. The alternate key (`assignment.user_no = device_history.user_no`) is **structurally impossible** (18-digit device vs 13-digit member).

**Match rate (PART 3, measured on the 3-day slice 06-01..06-03):** **15.22%** (> 5% → gate passes, key validated).
Per group (full window): control 60/3197 = 1.88%, variant1 74/3109 = 2.38%, overall **134/6306 = 2.12%**.
By join date: **06-01 = 111/172 (64.5%)**, 06-02 = 4/291, 06-03 = 1/299, ≈0 thereafter — see limitation below.

## PART 2 decisions

| # | Item | Decision |
|---|------|----------|
| 1 | **Join key** | `assignment.user_no = device_history.device_id_hash` → member `user_no` → `t_order.user_no`. (See above.) |
| 2 | **Device uniqueness** | `t_device_history` is NOT unique per `device_id_hash` (6 254 rows / 6 210 hashes / 5 895 members). Deduped to **one member per `device_id_hash`, earliest `create_time`** (= `register_dt`). 0 members mapped to both groups (no contamination). |
| 3 | **Date dim** | `dw_dim.dim_date_a` is Doris-only (unreachable). Replaced with computed dates. TZ: `pay_time`/`join_time`/`create_time` are UTC; NY = **fixed −4h (EDT)** — exact for the whole window (no DST change 6/1–6/23; verified `CONVERT_TZ(...,'UTC','America/New_York')` equals `−INTERVAL 4 HOUR`). `register_diffdate = DATEDIFF(dt, register_dt) ≥ 0` applied directly. |
| 4 | **Cups / drinks** | `t_order_item` has **no usable quantity** (`sku_num` is a "预留字段"/reserved field). Per the rule → **drinks = COUNT(line items)** of qualifying orders. Caveat: gift lines (`gift_flag=1`) are included. |
| 5 | **Orders + refund** | Dedupe grain: **every order has `parent_id == id`** (no split/child orders), so `COUNT(*)`/`COUNT(DISTINCT id)` is exact, zero inflation. Paid = **`status IN (20,90)`** (90 = completed dominates). Kept **`refund_status NOT IN (3,4,5)`**: empirically 2 = normal/no-refund (≈99%), 1 = refund-in-progress (kept); **5 = refund-completed** (`refund_time` always set), 4 = refunded, **3 = refund state without completion** (no `refund_time`/`cancel_time`) → excluding 3,4,5 drops refunded/closed orders. |
| 6 | **Register gate** | `register_uv(dt)` = cumulative distinct cohort **devices** with `register_dt` (NY) ≤ dt (`register_diffdate ≥ 0`), `register_dt = MIN(device_history.create_time)` per device. |

`dt_new_uuid` counts each device on its **first** join day (`MIN(join_time)`), so `Σ dt_new_uuid == total_ab_uuid` per group (asserted, passes). `total_ab_uuid` = distinct cohort devices per group.

## ⚠️ Material data limitation (must read before using order/register columns)

The RDS mirror of **`t_device_history` is FROZEN at 2026-06-02 08:47 UTC** (max `create_time` = `modify_time` = `login_time`; 66 rows on 6/2, none after). Because it is the only device→member bridge available (CDP `t_user_event_track` carries only the *raw* device id, not the reproducible hash; `t_user` has no device hash; the auth service has no device-login table), **order/register attribution resolves only the ~2.1% of cohort devices that were registered on/before 2026-06-02** (concentrated in 6/1 joiners, 64.5% of whom matched).

Consequently:
- **`dt_new_uuid` and `total_ab_uuid` are COMPLETE and correct** for every date (computed from the assignment table alone, no bridge needed).
- **`register_uv`, `order_uv`, `orders`, `drinks`, `revenue` are LOWER BOUNDS** — they reflect only the 134 bridge-resolvable devices (60 control / 74 variant1), whose orders are summed across the full window. `register_uv` plateaus after 6/2 (frozen bridge). These columns are **NOT a clean A/B readout** (coverage differs by group and is ~2%).
- On the intended live **Doris** warehouse (where `t_device_history` is presumably current) the identical logic would yield full coverage. This is the engine-substitution caveat called for in the brief.
