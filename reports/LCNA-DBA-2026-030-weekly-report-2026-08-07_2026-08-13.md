#### 1.2 上线过程中发现的缺陷：全绿测试一个也看不见

本周最有价值的部分。以下每一条在被发现前，测试都是全绿的。

| # | 缺陷 | 为什么测试看不见 |
|---|---|---|
| 1 | **抽取 schema 从写出来那天起就被 API 拒绝**（22 个 union 类型参数 / 上限 16），即**每一次抽取都 400** | 测试用的 `FakeLLM` 直接返回解析好的字典，schema **从不发送、从不校验**，唯一会校验它的是真实 API |
| 2 | **CORROBORATED 档此前无法达成** | 唯一能给产品挂第二条证据的路径匹配「同一篇稿子」，而独立性规则恰好排除正文近似的证据——能累积的证据正是不算数的那种 |
| 3 | **空环境变量被当成有值**：`ARGUS_CONFIG_DIR=` → `Path("")` → 内网 scheduler 从第一次 `up` 起就一直崩溃重启 | compose 输出的是 `Started`（那只表示进程被拉起过，不表示还活着）。我据此下过「Docker 已验证」的结论，下早了 |
| 4 | **`docker compose up -d` 不重建镜像**，代码烤在镜像里 | 连着三轮让人 `pull && up -d`，容器一直跑的是第一次构建的代码。**失败完全无声**：容器正常起、compose 报 Started，而刚拉的修复根本没在跑 |
| 5 | **`POSTGRES_*` 被宿主机 shell 劫持**：`.env` 写 `argus`，实际建出来的库属主是 shell 里的 `dba_admin` | 两边都能工作（建库连库都用 shell 那份），只有启动自检的比较看得出来。代价是 `.env` 里的值完全不起作用 |
| 6 | **`python -m argus.scheduler` 原本立刻退出**（模块没有 `__main__`） | 容器无限重启，**且显得健康**，什么都不采 |
| 7 | **引用校验误杀真实引用**：大小写未折叠、解析器自己在标点前插空格、`availability:"unknown"` 被要求引用一段证明不存在的文字 | 被污染的是「引用未通过」这个**信号**，而那正是人判断抽取可不可信的依据 |

**处置**：全部修复并补了钉死回归的测试（例如静态计数 schema 的 union 数，且计数器用真实报错标定）。

#### 1.4 部署形态与凭据边界

- **后端绝不上 Serverless**：调度器是常驻进程；爬取故意慢（一次 Dunkin' 跑 9 篇 93 秒，每 host 6 秒间隔）；限速 / robots 缓存 / 熔断状态跨源共享。Serverless 不会报错，只是**静默不再执行这些保证**。
- **凭据边界**：五个服务共用一个镜像，**只有 publisher 挂载 git 工作副本**（推送 token 在那个 checkout 的 remote 里）。爬虫是整天访问不可信站点的进程，给它推送权限没有任何收益。
- **API 服务已删除**：内网只能经 jumpserver SSH 进入，没有人用浏览器访问内网 → 那个服务的用户数是零，而它有四个**无鉴权**的写接口。复核改走命令行 `python -m argus.review`。

#### 1.5 发布调度搬入容器（08-13）

**动因是一次真实故障**：发布依赖一行宿主机 crontab，而那行**从来没人装过**。后果是 08-11 之后再没发布，看板悄悄超过陈旧阈值，而采集照跑、容器全 healthy——又是一次「看起来是好消息」。

改为 `publisher` 长驻容器 + 自带调度，时刻写进 `config/settings.yaml`。`docker compose up -d` 从此就是全部部署动作。**刻意不合并进 scheduler**（那会把推送凭据交给爬虫进程），有测试钉住这条边界。

#### 1.6 社媒接入：Instagram（08-13）

上新最早出现在社媒。三个平台评估后只有 Instagram 可行：Facebook 读别家主页需 App Review（此类用途批不下来），X 只有付费档能读，TikTok Display API 只能读自己。

- 走 Meta Graph API 的 `business_discovery`，**永久禁止爬 instagram.com**——其 robots.txt 明文声明「除非有书面许可，否则禁止以自动化方式采集」。有测试断言任何请求都不打该域名。
- **摆位是「探测器」**：IG 文案只够支撑产品名与首发时间，价格 / 供应期会留 NULL（证据规则正常工作，不是缺陷），靠与通稿源合并补全。
- 测试发现一处真实缺陷：**token 被拒原本被逐品牌兜底吞掉**，一个共享凭据失效被摊成六条相同警告 + 整轮记「部分成功」，读起来像「几个品牌有点问题」，实际一条都没采到。已改为整轮上抛。

### 主线二：`aws-luckyus-iopocp-rw` 主从切换根因分析（08-13）

报告：`reports/iopocp-failover-2026-08-13/report.md`

2026-08-13 15:02 UTC 发生 Multi-AZ 切换，历时约 65 秒。AWS 判定：`The RDS Multi-AZ primary instance is busy and unresponsive.`

**根因不是 CPU、不是内存、不是数据库故障，而是 EBS 吞吐额度耗尽后被限速。**

| 指标 | 切换前实测 | 判断 |
|---|---|---|
| `CPUUtilization` | 峰值 22.8% | ❌ |
| `CPUCreditBalance` | 最低 278（充足） | ❌ |
| `FreeableMemory` | 78–92 MB，全天平稳 | ❌ |
| `EBSIOBalance%`（IOPS 额度） | 全程稳在 75% | ❌ |
| **`EBSByteBalance%`（吞吐额度）** | **98% → 0%** | ✅ |

**根因链**：`t_event_info` 缺选择性索引 → 轮询查询每次全表扫 8 万行、返回 0 行，每小时 650–1600 次 → 128 MB 缓冲池要同时服务 2.9 GB 的大表，页被反复挤出 → 大量 4 KB 随机读打到 EBS → 08-13 上午轮询量翻倍（读 IOPS 82→105→133，常态 50–65）→ 额度 14:00 见底 → 查询从 2 秒变 44 秒 → 14:47 起连 CloudWatch 指标都发不出（**指标空洞本身就是无响应的独立证据**）→ 15:02 切换。

**两条判别方法值得沉淀**：

1. **必须分清两种 EBS 额度**。`EBSIOBalance%`（IOPS 次数）全程健康，`EBSByteBalance%`（吞吐字节）被打到 0。名字相近、含义不同，只看其中一个会得出相反结论。
2. **14:00 那 1,847 秒慢查询是果不是因**。判据是「最大扫描行数」全天恒定在 8 万左右——查询形状没变，变的是次数与被限速拖慢的耗时。误把它当根因去追「突然变慢的 SQL」，方向就反了。

**关键数据**：`t_event_info` 唯一可用索引首列 `key` 的**基数为 1**（全表仅 2 个不同值），对该查询等于不存在；而 `alarm_status`（11.3%）、`tenant`（11.6%）、`event_expire_time` 三个有选择性的列一个索引都没有。7 天内仅 08-13 见 0，前 6 天最低 27–48%——**该实例长期贴着吞吐上限运行，余量本就不厚**。
