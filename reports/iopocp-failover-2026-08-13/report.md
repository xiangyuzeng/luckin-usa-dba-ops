# aws-luckyus-iopocp-rw 主从切换 — 根因分析

**发起**：曾翔宇（DBA / Infra）
**日期**：2026-08-13
**相关方**：iopocp（运营管控平台 OCP）应用负责人 · Michael（实例规格变更）

---

## 零、结论先行

2026-08-13 15:02 UTC（11:02 EDT），`aws-luckyus-iopocp-rw` 发生 Multi-AZ 主从切换，历时约 65 秒。

**根因不是 CPU、不是内存、不是数据库故障，而是 EBS 吞吐额度（`EBSByteBalance%`）耗尽后被限速。**

触发它的是一条**缺索引的轮询查询**：每次全表扫 `t_event_info` 8 万行、返回 0 行，由两台应用机同时发出，每小时 650–1600 次。今天上午轮询量翻倍，把持续读吞吐推过了 db.t4g.micro 的基线，突发额度在 14:00 见底，实例随即失去响应。

**最高性价比的修复是加一个索引**（预期扫描 80,043 行 → ~0 行）。实例规格偏小是背景性问题，加完索引可以再观察。

## 三、排查过程与证据

### 3.1 先排除三个常见嫌疑

| 指标 | 切换前实测 | 判断 |
|---|---|---|
| `CPUUtilization` | 峰值 **22.8%** | ❌ 不是 CPU 打满 |
| `CPUCreditBalance` | 最低 **278**（充足） | ❌ 不是 CPU 积分耗尽 |
| `FreeableMemory` | 78–92 MB，**全天平稳，切换前无塌陷** | ❌ 不是触发因素（但见 3.4） |
| `SwapUsage` | 约 490 MB，**全天平稳，无骤增** | ❌ 不是 swap 抖动 |
| `DiskQueueDepth` | 峰值 0.27 | ❌ 不是排队积压 |
| `EBSIOBalance%`（IOPS 额度） | 全程稳在 **75%** | ❌ 不是 IOPS 额度 |
| **`EBSByteBalance%`（吞吐额度）** | **98% → 0%** | ✅ **就是它** |

**这里的关键判别是分清两种 EBS 额度**：`EBSIOBalance%` 管的是 IOPS 次数，全程健康；`EBSByteBalance%` 管的是吞吐字节数，被打到 0。两者名字相近但含义不同，只看其中一个会得出相反结论。

### 3.2 是今天才发生的，不是长期如此

`EBSByteBalance%` 每日最低点：

| 日期 | 最低 | ≤1% 的小时数 |
|---|---|---|
| 08-06 | 27.0% | 0 |
| 08-07 | 38.0% | 0 |
| 08-08 | 48.0% | 0 |
| 08-09 | 43.0% | 0 |
| 08-10 | 36.0% | 0 |
| 08-11 | 33.0% | 0 |
| 08-12 | 40.0% | 0 |
| **08-13** | **0.0% @ 14:00** | **1** |

日常会掉到 27–48% 再于夜间回满 —— 也就是说**这台实例长期贴着吞吐上限运行，余量本就不厚**，今天只是把它推过了线。

### 3.3 推过线的是负载翻倍

同一时刻的读 IOPS 逐日对比：

| 时刻 | 08-10 | 08-11 | 08-12 | **08-13** |
|---|---|---|---|---|
| 10:00 | 57.6 | 54.2 | 57.6 | **82.2** |
| 11:00 | 64.7 | 64.8 | 59.7 | **104.8** |
| 12:00 | 66.1 | 65.3 | 62.4 | **132.7** |
| 13:00 | 51.6 | 50.4 | 72.8 | 76.0 |
| 14:00 | 49.3 | 49.4 | 69.0 | 83.9 |

08-12 下午已有轻微抬头（69–73 vs 常态 50），08-13 上午则接近翻倍。

### 3.4 为什么这点吞吐就能耗光额度

切换前读吞吐只有 **0.25–0.70 MB/s** —— 数字很小，却在 13 小时内把额度排干。原因是**大量小块随机读**（约 130 IOPS × 4KB ≈ 0.5 MB/s，与实测吻合），而随机读之所以打到磁盘，是因为缓存装不下：

| 项 | 值 |
|---|---|
| `innodb_buffer_pool_size` | **128 MB** |
| 库总数据量 | **3,078 MB** |
| 缓存覆盖率 | **约 4.2%** |

其中 `t_shopsale_analysis_detail` 一张表就占 **2,929 MB**（1,034 万行，占全库 95%）。被反复扫描的 `t_event_info` 只有 80 MB，**本可以整张放进缓冲池**，但它得和那张 2.9 GB 的表抢同一个 128 MB —— 页一旦被挤掉，下一轮轮询就得回 EBS 重读。这是 I/O 的真正来源。

### 3.5 慢查询：分清「变慢是因还是果」

按小时聚合（08-13 UTC）：

| 小时 | 慢查询条数 | 累计秒 | 最长 | 最大扫描行 |
|---|---|---|---|---|
| 08:00 | 652 | 201.8 | 1.15s | 79,993 |
| 09:00 | 649 | 199.7 | 0.82s | 80,014 |
| 10:00 | 678 | 209.6 | 1.45s | 80,034 |
| 11:00 | 944 | 292.2 | 2.47s | 80,056 |
| 12:00 | 1,079 | 323.0 | 1.39s | 80,079 |
| 13:00 | 769 | 243.1 | 3.06s | 80,104 |
| **14:00** | **1,575** | **1,847.2** | **44.31s** | 80,131 |
| 15:00（部分） | 340 | 435.2 | 37.07s | 80,131 |

**14:00 那 1,847 秒是限速的结果，不是原因。** 判据是「最大扫描行数」全天恒定在 8 万左右（79,993 → 80,131，仅随表增长缓慢上移）—— 说明**查询形状没变**，变的是执行次数（11–12 点）和单次耗时（14 点，被限速拖慢）。如果误把 14 点的 44 秒当成根因去追某条「突然变慢的 SQL」，方向就反了。

### 3.6 元凶 SQL

```sql
SELECT id, `key`, name, type, type_key, locality_mid, metrics, reason_keys,
       occur_time, status, confirm_time, confirm_reason, confirm_emp,
       push_posts, push_emp_names, push_content, push_time, ...   -- 30+ 列
FROM t_event_info
WHERE alarm_status = 1
  AND event_expire_time < '2026-08-13 11:25:30.081'
  AND `key` IN ('EVENT_SHOP_PRESSURE')
  AND tenant = 'LKUS';
```

- `Rows_examined: 80,043` / `Rows_sent: 0` —— **每次全表扫，每次什么都不返回**
- 由 `iopocp_A_o` 从 **10.238.42.197** 和 **10.238.38.89** 两台应用机发出
- 两条日志时间戳相差 **5 微秒**（11:25:32.551359 / .551364）→ 是两个实例上的同一个定时任务同时触发，不是用户请求

### 3.7 为什么走不了索引

`t_event_info` 的索引现状：

| 索引 | 列 | 基数 |
|---|---|---|
| PRIMARY | `id` | 83,691 |
| `idx_key_type_typeKey` | `key` | **1** |
| | `type` | 1 |
| | `type_key` | 53 |

**`key` 的基数是 1** —— 全表实际只有 2 个不同值。`key IN ('EVENT_SHOP_PRESSURE')` 匹配几乎所有行，这个索引对该查询等于不存在。

而真正有选择性的三个列**一个索引都没有**：

| 谓词 | 匹配行数 | 占比 |
|---|---|---|
| 全表 | 90,248 | 100% |
| `alarm_status = 1` | 10,234 | 11.3% |
| `tenant = 'LKUS'` | 10,438 | 11.6% |
| `alarm_status=1 AND tenant='LKUS'` | 9,799 | 10.9% |
| 再叠加 `event_expire_time < NOW()` | 9,791 | 10.8% |
| **再叠加 `key='EVENT_SHOP_PRESSURE'`** | **0** | **0%** |

## 四、根因链

```
t_event_info 缺选择性索引
   → 轮询查询每次全表扫 8 万行、返回 0 行
   → 128MB 缓冲池要同时服务 2.9GB 的 t_shopsale_analysis_detail，页被反复挤出
   → 大量 4KB 随机读打到 EBS
   → 08-13 上午轮询量翻倍，持续吞吐超过 t4g.micro 基线
   → EBSByteBalance% 98% → 0%（14:00）
   → EBS 吞吐被限到基线，查询从 2 秒变 44 秒
   → 实例失去响应（14:47 起连指标都发不出）
   → RDS 健康探测失败 → Multi-AZ 切换（15:02:26 → 15:03:31）
```

**说明**：AWS 不公开健康探测的内部细节，「限速 → 无响应」这一步是基于时序与机制的推断，而非 AWS 明示。支撑它的是三条独立证据：额度归零、慢查询时长同步暴涨 6 倍、以及紧随其后的 14 分钟指标空洞。

## 五、建议

### ① 加索引 —— 最高优先级，**需变更审批**

```sql
ALTER TABLE luckyus_iopocp.t_event_info
  ADD INDEX idx_tenant_alarm_key_expire (tenant, alarm_status, `key`, event_expire_time);
```

等值列（`tenant` / `alarm_status` / `key`）在前，范围列 `event_expire_time` 必须放最后。

- 预期效果：扫描 **80,043 行 → ~0 行**
- 表仅 90,248 行 / 80 MB，DDL 很快；但**仍建议走变更窗口**，因为实例当前吞吐余量不厚
- 本次排查**未执行任何变更**，以上为建议

### ② 请 iopocp 应用侧确认 —— 需应用负责人

- 该轮询的**频率是否有必要**（每小时 650–1600 次、每次返回 0 行）
- 两台实例**是否必须同时触发**（错开可以削峰）
- **过期事件是否有清理任务**：`t_event_info` 约每小时增长 150 行，全表扫的代价随时间线性变差。今天一天内 `Rows_examined` 就从 79,993 爬到 80,131

### ③ 实例规格评估 —— 需 Michael

1 GB 内存 / 128 MB 缓冲池承载 3 GB 数据，swap 常驻约 490 MB，`EBSByteBalance%` 日常最低仅 27–48%。加完索引应能缓解，但 `t_shopsale_analysis_detail` 仍在增长，建议纳入升配评估。

### ④ 两个隐患（暂未咬人，建议顺手处理）

- **`max_connections = 4000`，而实例只有 1 GB 内存。** 当前实连仅约 20，所以没出事；但完全没有护栏，一次连接风暴会直接打死实例。
- **建议加 CloudWatch 告警**：`EBSByteBalance%` < 30% 持续 15 分钟。本次事故在触 0 之前有约 3 小时的下降过程（11:00 已跌到 45%），是有充足预警窗口的，只是没人在看这个指标。
