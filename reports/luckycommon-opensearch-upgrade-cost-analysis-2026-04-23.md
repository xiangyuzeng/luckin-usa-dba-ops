## 整改方案成本对比

### 方案说明

| 方案 | 描述 | 解决的问题 |
|---|---|---|
| **A** | Master 升级: 3× t3.small → 3× m5.large | 消除突发实例作为 master 的不稳定性 |
| **B** | 数据节点升级: 4× m5.large → 4× r5.large | 增大 JVM heap (4GB→~10GB)，缓解慢性内存压力 |
| **C** | A + B 合并 | 同时解决 master 稳定性和 JVM 压力 |
| **D1** | 添加副本分片（现有容量内） | 消除 0副本分片导致的 RED 风险，零成本 |
| **D2** | 添加副本 + EBS 扩容至 150GB/节点 | D1 + 额外存储余量 |

### 成本对比表

| 方案 | 变更内容 | 月增量成本 | 相对当前 | 年化增量 |
|---|---|---|---|---|
| **当前** | 4×m5.large + 3×t3.small + 400GB gp3 | **$374.17/月** | 基线 | — |
| **A: Master 升级** | 3× t3.small → 3× m5.large | **+$160.18/月** | +42.8% | +$1,922/年 |

### 详细计算

**方案 A — Master 升级**
```
当前:  3 × $0.036/hr × 730h × 0.69 = $54.40/月
升级后: 3 × $0.142/hr × 730h × 0.69 = $214.58/月
增量:  $214.58 - $54.40 = +$160.18/月
```

**方案 B — 数据节点升级**
```
当前:  4 × $0.142/hr × 730h × 0.69 = $286.10/月
升级后: 4 × $0.186/hr × 730h × 0.69 = $374.75/月
增量:  $374.75 - $286.10 = +$88.65/月
```

**方案 C — A+B 合并**
```
增量: $160.18 + $88.65 = +$248.83/月
升级后总成本: $374.17 + $248.83 = $623.00/月
```

**方案 D1 — 添加副本分片（无需扩容）**
```
当前存储使用: ~223GB (ClusterUsedSpace)
总 EBS 容量:  400GB (4×100GB)
添加副本估算: ~18个分片 ≈ 18/59 × 223GB ≈ 68GB
使用后总量:   223 + 68 = ~291GB < 400GB ✓
结论: 现有存储容量足够，无需额外成本
```

**方案 D2 — 副本 + EBS 扩容**
```
当前:  400GB × $0.122/GB-月 × 0.69 = $33.67/月
扩容后: 600GB × $0.122/GB-月 × 0.69 = $50.51/月
增量:  $50.51 - $33.67 = +$16.84/月
```

## 建议执行顺序

| 优先级 | 方案 | 成本 | 理由 |
|---|---|---|---|
| **1 (立即)** | **D1: 添加副本** | $0/月 | 零成本消除 RED 告警最大风险源 |
| **2 (1-2周)** | **A: Master 升级** | +$160/月 | 消除 t3 突发实例的 master 不稳定性 |
| **3 (评估)** | **B: 数据节点升级** | +$89/月 | 缓解 JVM 压力，可结合 ES→OS 升级一并执行 |
| **4 (可选)** | **D2: EBS 扩容** | +$17/月 | 如副本添加后存储余量不足再执行 |

> **推荐组合**: D1 + A = **+$160.18/月 (+42.8%)**，解决最紧迫的两个问题（无副本 + master 不稳定），年化增量约 $1,922。
