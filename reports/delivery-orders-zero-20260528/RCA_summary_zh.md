# LCNA-INC-2026-XXX — 宙斯告警「过去1小时外卖订单跌到0」根因分析 (2026-05-28)

**结论：告警机制正确,本质为低峰时段稀疏流量自然波动,无系统故障。建议降级至周报跟进 + 调优告警阈值。**

---

## 一、现象

- 告警平台：宙斯 (Zeus),策略组「中美-运维告警协作群」
- 策略名称：【北美-业务告警】过去1小时外卖订单跌到0
- 告警级别：P2(初判),实际无业务影响,**建议降为周报/调优工单**
- 触发时间:2026-05-28 17:57 EDT (21:57 UTC),恢复时间:18:57 EDT (22:57 UTC),持续约 60 分钟
- 渠道范围:channel_id ∈ {8 DoorDash, 9 Grubhub, 10 UberEats}
- 策略来源:由旧策略 id=105 迁移而来

## 三、根因(假设排查矩阵)

| 假设 | 排查证据 | 结论 |
|---|---|---|
| H1 数据管道断流(CDC / 采集器异常) | 采集层 t_collect_order_inter 与 t_order 逐条对应,延迟约 60 s | **排除** |
| H2 事务库异常(连接风暴 / 主备切换 / 锁阻塞) | CloudWatch 显示连接数/CPU 持续平稳,RDS Events 与 CloudTrail 均为空 | **排除** |
| H3 id=105 迁移导致 SQL/表/列错位 | 恢复时间(22:57 UTC)精确出现在首笔后续订单(22:56 UTC)之后 1 分钟,说明告警 IS 在跟踪真实数据 | **排除** |
| H4 真实业务波动(本次主因) | 内场渠道 1/2/3 期间全程正常,仅外卖渠道 8/9/10 空窗;14 天基线显示该时段每 3 – 4 天出现一次空窗 | **成立(高置信度)** |
| 外卖平台回调中断(DoorDash / UberEats / Grubhub) | 三家平台均在约 1 小时后自然恢复,未发现 status pileup 或厂商侧故障通报 | 不成立 |

### 与 5/29 案例的区别

- **5/29 12:00 – 14:00 ET**:真实订单 7 笔 + 采集层 7 笔 + 告警显示 0 → **gauge 与真实数据解耦**,属虚警(未解决,仍需订单服务侧排查)
- **5/28 21:55 – 22:55 UTC**:真实订单 0 + 采集层 0 + 告警显示 0 → **告警机制正确**,只是阈值对稀疏渠道过于敏感

迁移后的策略有两个独立问题:**gauge 解耦(5/29 案例)** + **阈值过敏(5/28 案例)**。

## 四、业务影响

- **实际客户影响:无。** 内场堂食 / 移动端 / 小程序在告警期间全程正常,外卖渠道在 62 分钟后自然恢复。空窗与历史同时段统计噪声范围一致。
- **数据完整性:无丢失。** 两层数据完全对账,无 CDC / 主从复制差异。

## 五、整改建议

| 优先级 | 措施 | 责任方 |
|---|---|---|
| P2 | **降低告警敏感度**:`sum(...)==0` 仅在 7 天历史同小时均值 > 5 时触发,或将 `for` 改为 2 小时(连续两小时空窗才告警) | 监控团队 |
| P2 | **修复 ET 时间窗 bug**(由 5/29 RCA 转入):`hour()` 返回 UTC,当前表达式 `12<hour()<=22` 实际对应 09:00 – 18:00 EDT,而非预期的 12:00 – 22:00 EDT,导致**晚餐高峰(18:00 – 22:00 EDT)被静默** | 监控团队 |
| P3 | **加内场对照守卫**:`AND sum(business_order_channel_count{channel_id=~"1\|2\|3"}) > 0`,确保内场有量时才认定外卖 0 异常,防止管道故障被误归类 | 监控团队 |
| P3 | **追溯 id=105 迁移文档**,同时记录 5/29 false-positive 与 5/28 噪声两类问题 | 监控 + 订单服务团队 |
