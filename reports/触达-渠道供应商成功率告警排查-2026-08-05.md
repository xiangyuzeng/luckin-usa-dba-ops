**排查时间**：2026-08-05 · **排查人**：曾翔宇（DBA）
**告警状态（截至排查时）**：**FIRE 中，持续 4 小时 21 分，未认领、未静默、已被 Zeus 自动升级**

---

## 一句话结论

**数值属实，但不是供应商故障，也没有影响任何业务短信。**
成功率被 `cyberdata` 服务的**运维告警短信**拖垮 —— 它每天向**同一个中国大陆号码**发约 6,100 条短信，
占 LKUS 全部短信量的 **56%**，而这条跨境通道的送达率天然只有约 9%。
面向美国用户的真实业务短信（验证码 / 通知 / 营销）成功率一直是 **98–99%**，正常。

## 四、根因

```
cyberdata 服务持续产生 ops 告警
        ↓  每约 14 秒一条短信
收件人 = 单个中国大陆手机号（+86）
        ↓  跨境路由
走 zthy 国内短信通道 → 送达率天然仅约 9%
        ↓  每天 ~5,550 条失败
污染「渠道供应商成功率」分母（占全量 56%）
        ↓
整体成功率 98% → 39%，触发 P0 告警
```

**两层问题**：
1. **应用层**：`cyberdata` 的运维告警在刷屏 —— 每天 6,000+ 条告警短信本身就说明告警没有收敛。
2. **指标层**：业务短信与运维短信混在同一个成功率分母里，导致该指标无法反映业务健康度。
   这也解释了它为什么连续告警一个月无人处理：数字很吓人，一查不影响业务，于是搁置。

## 五、建议动作

| # | 动作 | 责任方 | 优先级 |
|---|------|-------|-------|
| 1 | 停掉 / 收敛 `cyberdata` 的 ops 告警短信（每 14 秒一条是告警风暴，不是短信问题） | cyberdata 应用团队 | **P1** |
| 2 | 「渠道供应商成功率」指标按 `busi_type` 拆分，或直接排除 `ops` 类，使其只反映业务短信 | 触达平台 / 监控 | **P1** |
| 3 | 中国大陆号码接收运维告警，改用飞书 / 邮件，或换支持跨境的通道 | cyberdata + 触达平台 | P2 |
| 4 | 认领或静默当前这条告警，避免继续挂着 | 值班 | P2 |
| 5 | 复核阈值：70% → 65% 的下调没有解决问题，建议在指标口径修正后重设 | 监控 | P2 |

**待确认的线索（假设，无证据）**：`cyberdata` 正是 `meta-platform-rel` 两个 Pod 所在的
namespace（`cyberdata-prod`）—— 即告警月报中那个跨 25 天反复 OOM、判定为内存泄漏的服务。
ops 告警短信轰炸是否与之同源，建议应用团队一并核查。

## 附录：复现命令

```sql
-- 1) 告警本身（Zeus）
SELECT alert_time, alert_status, claimed_status, alert_upgrade_status, summary
FROM luckyus_izeus.t_alert WHERE del_flag=0 AND strategy_id=208 ORDER BY id DESC;

-- 2) 按供应商拆成功率
SELECT statistics_date, provider, sms_type, SUM(deliver_count) submitted,
       SUM(receipt_success_count) succ, SUM(receipt_fail_count) fail,
       ROUND(100*SUM(receipt_success_count)/
             NULLIF(SUM(receipt_success_count)+SUM(receipt_fail_count),0),2) rate
FROM luckyus_iupushsms.sms_statistics_record
WHERE tenant='LKUS' AND statistics_date >= '2026-07-27'
GROUP BY 1,2,3 ORDER BY 1 DESC, 4 DESC;

-- 3) 失败是否集中在单一号码
SELECT provider, area_code, state, COUNT(*) n, COUNT(DISTINCT mobile) distinct_mobiles
FROM luckyus_iupushsms.sms_receipt_0005
WHERE tenant='LKUS' AND send_time >= '2026-08-04'
GROUP BY 1,2,3 ORDER BY n DESC;

-- 4) 发送方归属
SELECT app_name, busi_type, provider_account, state, COUNT(*) n, DATE(send_time) d
FROM luckyus_iupushsms.sms_receipt_0005
WHERE tenant='LKUS' AND area_code='86' AND send_time >= '2026-08-01'
GROUP BY 1,2,3,4,6 ORDER BY d DESC, n DESC;
```

数据源：`aws-luckyus-devops-rw`（`luckyus_izeus`）、`aws-luckyus-upush-rw`（`luckyus_iupushsms`），全部为只读查询。
