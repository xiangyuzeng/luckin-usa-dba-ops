#### 1.1 两个统计口径缺陷：平台一直在把失败算成成功

这是本期最值得记的一条，因为**它污染的是此前每一份告警周报/月报的质量指标**。

| # | 缺陷 | 机理 | 实际影响 |
|---|---|---|---|
| 1 | **`claude -p` 的报错被当成分析报告存了下来** | 该 CLI 把自己的失败打到 **STDOUT 且退出码为 0** → `ask()` 把错误文本当分析内容返回。流水线本来有正确处理路径（重试一次 → 记 `record_kind='failed'` → 跳过人工渠道），但**这条路从没走到过**，因为"返回非空"看起来就是成功 | 2026-06-17 ~ 08-04 共 **6 行**这样进了统计表（4 条 `529 Overloaded`、2 条响应中断）。每一条都被计为"已分析告警"，并**作为飞书卡片推给了人**，卡片正文全文就是 `API Error: 529 Overloaded` |
| 2 | **「其中已 AI 分析」的分母是错的** | 它等于"所有非去重行"，于是把平台**按设计就不分析**的行（info 级、被静默、分析失败）也扫了进去。这些行的 `analysis` 字段是一行占位符而不是报告 | 稀释了所有基于同一集合计算的质量指标：根因标签覆盖率、检出到出报告时延、"未提取到结论"卫生检查 |

**W32 那份报告是暴露问题的案例**：它写着「9 条已分析告警未提取到结论段落」，
并据此建议「扩充 `database_notifier` 的 heading 关键词」。
实际上那 9 条 = **7 条 info 行 + 2 条失败运行 + 0 条真正的提取遗漏**——
**它建议的整改修不了任何东西**。更正后该周读作 25 已分析 / 11 去重 / 7 info / 2 失败 = 45 总量，
概览表现在直接把这个拆分显示出来，以便被审计。

**检测锚点定在输出开头是刻意的**：所有真实报告都以 `## 告警分析报告` 起头
（已存的 518 份报告无一例外），而**限流类告警的分析正文里合法地会讨论 "rate limit" / "API Error"**

#### 1.2 新增 `rds_failover` skill：切换告警先看 EBS 额度，再看 CPU

**动因是一个可量化的覆盖缺口**：`【DB告警】AWS RDS 发生重启或者主从切换` 累计触发 **61 次**，
全部由通用 `rds` skill 处理，而该 skill 的步骤覆盖 CPU / 连接 / 内存 / IOPS / 慢查询，
**唯独不含 `EBSByteBalance%`**——**61 份分析里提到它的次数是 0**。

这不是理论缺口。08-13 当天 `iopocp` 与 `scm-ordering` 双双以
"The RDS Multi-AZ primary instance is busy and unresponsive" 切换，两起**都是 EBS 吞吐额度耗尽**，
而 CPU 全程 6–23%、内存平稳。平台分析了这两起（id 773/774），结论是
「真实重启，已恢复正常，业务影响很小」——**就事实而言没错，作为建议则恰好完全错了**：
iopocp 若不加索引，第二天早上会再次耗尽。

新 skill 把顺序倒过来（额度优先、CPU 其次），并把这次真正花了时间才辨出来的判别点写进提示词：

- `EBSIOBalance%` vs `EBSByteBalance%`——健康的那个和耗尽的那个长得几乎一样；
- **指标空洞本身就是"无响应"的证据**，不是"监控没采到"；
- **`Rows_examined` 最大值恒定 = 慢查询是果不是因**；
- 内存判据用 **buffer pool 空闲页**，不是全库大小；
- **重启后的预热不要误读成负载回来了**。

#### 1.4 飞书分发：多群 + @ 到人

- **多群**：一个群 = 一个自定义机器人 = 一个 webhook URL。URL 里带 token，
  所以 `config.yaml` 里只放**环境变量名**，值留在 `.env`。一个群做 catch-all 收全量，
  其余群按订阅切片（实例 glob / 告警类型 / 级别下限）收副本。
  **路由规则是最容易打错的部分，而打错的代价必须是"专项群少收一条副本"，不能是"告警本身丢了"。**
  - 回归测试逮到的一个真实后果：初版在群自己声明了 `webhook_env` 但该变量未设置时会**回落到全局 URL**
    ——即变量名打错不会跳过该群，而是**往主群里多发一份**，这是更难被发现的失败模式。已改为不回落。
- **@ 到人**：负责人表 bind-mount 进容器，**改完不用重建也不用重启**，下一条告警即生效。

#### 1.5 负责人表：从 glob 通配改为精确枚举（一次设计返工）

初版用 glob 前缀匹配推断归属。**这个设计被否掉了，理由成立**：
归属是**组织事实**，不是字符串的属性。`aws-luckyus-scmcommodity-rw` 与 `aws-luckyus-scm-ordering-rw`
看起来像一家，完全可能分属不同团队——**用共同前缀去认领两者就是在猜，
而对"谁半夜被叫醒"这件事做猜测，比留一个明确的空缺更糟。**

一并删掉的还有整套 glob 机制（特异性排序、字面前缀 tiebreak、两条规则打平时合并 owner）——
那些复杂度**只是在给自己收拾烂摊子**，处理的都是精确名字根本不会产生的重叠。
现在的查找是：精确实例名 → workload 前缀（仅 K8s Pod，因为 Pod 名带每次发布都变的 hash，无法枚举）→ fallback。

- 实例集是**有限可枚举**的：**77 个 RDS + 79 个 Redis = 156 个全部列出**，
  且**从 AWS 实拉**而非手抄。
- 域归属只依据 `CLAUDE.md` 里记录的服务清单；**没记录的一律进显式的「未分派」组**，
  而不是按名字相似度安置——那是同一个猜测换了身衣服。
- 精确名字换来了通配做不到的一件事：`check_owners.py --live` 可以**双向**与 AWS 实际清单对账
  ——没人认领的实例是**看得见的**，而新建实例在有人指派之前默认就是无主的，**这才是正确的默认值**。
- `feishu_id` 补了获取文档 + 批量解析器。三个关键点：填姓名/邮箱/手机号一律无效；
  外部群只认 Open ID；**填错 ID 飞书不会报错**，@ 只渲染成一段灰字，发送方完全看不出来
  → 先用 `check_mention.py` 验一个再批量填。

### 主线三：`isalestradecapi` SocketTimeout P1 研判（08-19）

报告：`reports/2026-08-19-isalestradecapi-sockettimeout/RCA.md`

**结论：不是数据库/缓存/节点故障，DBA 侧全部指标健康。**

根因链：`iriskcontrolservice` 的**单个 Pod**（`...-tblvn` / 10.238.42.255）**所有接口**被固定卡在 **~6.35–6.40 秒**
→ 约一半风控调用走到这个 Pod → `isalestradecapi` 调风控的 HTTP 读超时被打爆 → `SocketTimeoutException`。

| Pod | 18:00 前 | 18:05–18:35 |
|---|---|---|

  又让 ozono 里那条正常的在营记录落进 `db_only`，被报成"改名/非 ElastiCache?"

形态为 79 个 cluster mode 关 + **1 个开**；**73 TLS / 7 非 TLS**。

#### 5.2 `--expand-shards`：clustercfg 单 target 会让指标全废

实测：`clustercfg.…` **一条 DNS 名解析出全部 6 个节点的 IP**（3 主 3 从），
且**服务端每次查询轮换顺序**（30 次采样近似均匀落在 6 个节点上）→ **每次 `/scrape` 落到随机节点**。后果：

| 症状 | 后果 |
|---|---|
| counter 类指标在同一 `instance` 下混了 6 个互不相干的计数器 | `rate()`/`increase()` 被当成 counter reset → **凭空尖峰或恒为 0**，命令率/命中率全不可信 |
| `redis_memory_used_bytes` / `redis_db_keys` 是单节点值 | 只看得到 1/N 且在分片间跳变，容量水位**既可能虚低也可能误报** |
| 单个分片挂掉 | 只有约 1/N 的抓取会落在它上面 → **间歇告警易被当噪声，或被完全掩盖** |

`--expand-shards` 调 `describe-cache-clusters --show-cache-node-info` 取每节点端点
（**故障转移只换角色不换端点**，适合当 target），展开成 N 个独立 target，一节点一条时间序列。

**三个必须知道的点**：
1. **crontab 的 `--cron` 必须带同样的开关**，否则算出的 targets 与现网文件不同 → **天天误报漂移**。
2. **密码文件会刻意保留 clustercfg 那个父 key**——token 的权威来源是现有密码文件，
   若展开后只剩节点 key，下一轮就查不到父 key → 报 `token_missing` 并置空 → 再 `--apply`
   会把 N 个节点的 token 全清掉，**即 2026-07-16 事故的翻版**。有幂等单测 + 反证用例守着。
3. 拿不到节点端点时**绝不半写**：`--cron` 降级告警恒退出 0，`--apply`/dry-run 干净退出非 0。

#### 5.3 那条唯一的告警，被飞书限频吞掉了

**这是本期主题最直白的一例**：08-20 早晨的 cron 正好带着 `db_only=1`（就是上面那个漏监控）去告警，
却吃到飞书 `code=11232 frequency limited` —— **告警被限频吞掉，只落进日志没人看**，
漏监控就这么"没人发现"。同一个飞书机器人被 alert-daemon 等多方共用时很容易撞限频。

已加三层处置：
- **限频自动重试**：共 3 次尝试，间隔 2s/6s，每次重签名。判定走纯函数 `feishu_retryable(code, msg)`
  ——**code 与 msg 双判据**，因为飞书限频有一族相近 code；签名错(`19021`)/参数错这类重试也没用的**立即放弃**。
- **送不出去时留可 grep 的标记**：重试耗尽后日志打 `[ALERT-UNDELIVERED]` + 完整标题正文。
  `--cron` 恒退出 0，日志是唯一线索 → 建议加巡检 `grep -c ALERT-UNDELIVERED`。
- **webhook URL 不进日志**：末段就是机器人 token，一律经 `redact_webhook()` 掩码（此前成功分支会打完整 URL）。
