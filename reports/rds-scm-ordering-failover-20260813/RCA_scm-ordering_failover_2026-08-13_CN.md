## 1. 摘要

实例确实发生了 Multi-AZ 主从切换并重启。AWS 官方事件原因为：
**"The RDS Multi-AZ primary instance is busy and unresponsive."**（主实例繁忙且无响应）

直接原因：**EBS 吞吐额度（`EBSByteBalance%`）耗尽**。2026-08-13 13:00 UTC 起，实例上出现了一段
**异常读负载**（ReadIOPS 由 5–25 升至 70–130 并持续），使 `EBSByteBalance%` 在 8.5 小时内由 99%
单调耗尽至 0%；额度归零后 EBS I/O 被限速至基线，主实例无法继续提供 I/O 服务，RDS 触发切换。

期间 CPU（6–11%）、内存、连接数（13–18）全程平稳 —— **与业务量、锁等待均无关。**

**该异常负载已于切换时终止**（很可能是被重启中断），额度已自行恢复至 99%，
**无即时复发风险**。真正待解决的是：**13:00 UTC 那段负载到底是什么**，以及**缺失的额度告警**。

## 3. 证据

### 3.1 耗尽的是吞吐（字节）额度，不是 IOPS
| 指标 | 13:00 → 21:35 表现 |
|------|---------------------|
| `EBSByteBalance%` | **99% → 0%**，单调下降 ← 已耗尽 |
| `EBSIOBalance%` | 平稳在 74–75% ← 全程无风险 |
| `BurstBalance` | 无数据点（gp3 卷不适用该指标） |
| `CPUUtilization` | 6–11%，平稳 |
| `FreeableMemory` | 约 90–108 MB，平稳（无泄漏、无骤降） |
| `DatabaseConnections` | 13–18，平稳 |
| `ReadLatency` | 约 0.7 ms，限速前平稳 |

CPU、内存、连接数均可排除常见的切换诱因。唯一触及上限的指标就是 EBS 字节额度。

### 3.2 切换后已自行恢复（v2 新增实测）

| 时间 (UTC) | 21:55 | 22:00 | 22:10 | 22:25 | 22:40 | 22:50 |
|---|---|---|---|---|---|---|
| `EBSByteBalance%` | 99 | 98 | 97 | 98 | 98 | **99** |
| ReadIOPS | 74 | 134 | 27 | 45 | 18 | **7** |
| ReadThroughput | 467 KB/s | 887 | 154 | 259 | 104 | **41 KB/s** |

额度下探至 97% 后**回升至 99%**；ReadIOPS 回落至 7–20，即 13:00 之前的基线水平。

数据库内部指标印证：切换后 52 分钟内 InnoDB 仅发生 **308 次物理读**（约 0.1 次/秒）。

### 3.3 实例规格评估（v2 重要修正）

| 项目 | 数值 |
|------|------|
| 实例规格 | `db.t4g.micro`（1 GB 内存，2 vCPU） |
| `innodb_buffer_pool_size` | 128 MB（8192 页 × 16 KB） |
| **稳态已用数据页** | **7,123 页 ≈ 114 MB** |
| **空闲页** | **1,068 页 —— buffer pool 并未占满** |
| 稳态命中率 | **98.3%** |
| 全库大小（`luckyus_scm_ordering`） | 约 800 MB（含冷数据，非热数据量） |
| 最大表 `t_auto_order_small_log` | 243.6 MB（169 万行） |

**结论：稳态下该实例并不存在内存瓶颈。** 热数据约 114 MB，128 MB 的 buffer pool 足以容纳且尚有空闲。

> v1 曾记录命中率 92.9% —— 那是在重启后 385 秒（缓存尚冷）时的采样值，不代表稳态。

**关于 128 MB buffer pool 的说明：** 这**并非**参数组配置缺陷。参数组 `luckyus-prod-84` 中该参数
未显式设置，由 MySQL 依据探测内存自动伸缩。已用反例验证：`aws-luckyus-salesmarketing-rw`
（db.t4g.xlarge，**同一参数组**）的 buffer pool 为 11,520 MB。

### 3.4 EBS 带宽核算（v2 新增）

AWS 官方规格（已核实）：

| 规格 | EBS 基线带宽 | 基线吞吐 | 突发上限 |
|------|--------------|----------|----------|
| t4g.micro（现状） | 87 Mbps | **10.88 MB/s** | 260.62 MB/s |
| t4g.small | 174 Mbps | 约 21.7 MB/s | 260.62 MB/s |
| t4g.medium | 347 Mbps | 43.38 MB/s | 260.62 MB/s |

**故障期间实测读吞吐：平均 0.4–0.97 MB/s，1 分钟峰值仅 3.37 MB/s** —— 尚不足 micro 基线
（10.88 MB/s）的三分之一。

**这意味着：额度耗尽无法用"分钟级平均吞吐超过基线"来解释**，只能来自被分钟级平均值抹平的
**秒级突发**。该机理尚未完全查清，因此**不宜以"需要更高基线带宽"为由论证升配**。

### 3.5 具体问题 SQL（仍然有效）

**(a) 缺少联合索引 —— `t_shop_order_calendar_warehouse_history`（26 万行）**

```sql
SELECT max(dt) FROM t_shop_order_calendar_warehouse_history
WHERE shop_dept_id = ? AND wh_dept_id = ? AND tenant = 'LKUS';
-- Rows_examined：152,951–160,384   Rows_sent：1
```
现有索引全部是**单列索引**：`idx_shop`（基数 24）、`idx_warehouse`（基数 4）、
`idx_dt`（基数 113）、`idx_operated_time`。无联合索引，优化器只能沿 `idx_dt` 倒序遍历再过滤，
为返回 1 个值需扫描全表约 60% 的数据。且以「按门店循环」方式调用。

**(b) 索引前缀失配 —— `t_auto_order_small_log`（169 万行，243.6 MB）**

```sql
SELECT small_class_mid FROM t_auto_order_small_log
WHERE shop_dept_id = ? AND order_date = ? AND tenant = ?;
-- 平均每次执行 143 ms，返回约 214 行
```
唯一二级索引为 `uniq_shop_small_order_date` =
`(shop_dept_id, small_class_mid, order_date, tenant)`。查询**未**过滤第 2 位的
`small_class_mid`，因此只能用到 `shop_dept_id` 前缀，之后须扫描该门店全部索引条目。

### 3.6 未查清的部分（如实说明）

1. **13:00 UTC 异常负载的来源未定位。** `performance_schema` 在 21:55 重启时被清空
   （仅剩约 20 分钟历史），且 `long_query_time = 0.1` 使慢查询日志看不到真正贡献 I/O 的
   百毫秒内语句。**这是当前最大的未知项。**
2. **秒级突发耗尽额度的具体机理未完全查清**（见 3.4）。

**→ 需运维团队确认：** 2026-08-13 **13:00 UTC（美东 09:00）** 前后是否有发版，或批处理 /
定时任务调度变更？该负载持续约 9 小时后随重启终止。

### 3.7 全局巡检 —— 无其它实例处于风险中

已对全部 RDS 实例扫描 `EBSByteBalance%`。`scm-ordering` 曾是唯一异常项（现已恢复 99%）；
**其余所有实例均在 99–100%**，包括同日早些时候以相同机理切换过的 `iopocp`。
共 61 台实例共用参数组 `luckyus-prod-84`，其中 **32 台是 db.t4g.micro**。

## 5. 排查经验沉淀

1. **指标空洞本身就是证据。** 21:39–21:54 所有 CloudWatch 曲线断档，正是"无响应"这件事本身。
2. **重启后的指标回升是缓存预热，不是负载恢复。** 这是本次 v1 判断失误的直接原因 ——
   评估切换后是否仍有风险，**至少要观察到预热结束（约 15–30 分钟）之后**再下结论。
3. **全库大小 ≠ 工作集。** 判断内存是否够用，应看 `Innodb_buffer_pool_pages_data` /
   `pages_free` / 稳态命中率，而不是 `information_schema.tables` 的容量汇总。
   **buffer pool 尚有空闲页 = 内存不是瓶颈。**
4. **慢查询数量可能是果，不是因。** `long_query_time = 0.1` 下，一旦 I/O 阻塞，日志会被
   `SELECT 1` 这类语句刷屏。21:30 的 1,111 条尖峰是被限速的结果，而非触发原因。
5. **burstable 实例上，先看额度类指标，再看 CPU。** 今日两次切换 CPU/内存都完全正常。
