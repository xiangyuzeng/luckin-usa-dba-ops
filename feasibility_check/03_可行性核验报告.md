# A 组：决定看板能不能做

## F-01｜排班是否精确到班次级起止时间（B-03，P0）

**结论：🟡 部分可实现。** 排班确实是班次级明细、精确到分钟，但起止时间以字符串存储，需要在 ETL 层解析；一天多班次的情况存在但很少。

### 排班数据在哪张表

`aws-luckyus-opempefficiency-rw` → `luckyus_opempefficiency.t_emp_scheduling`（表注释「人员排班工时详情表」）。

同库另有 4 张排班相关表，全部排除：`t_emp_scheduling_summary`（0 行，注释标「-- 弃用」）、`t_emp_scheduling_summary_detail`（0 行，「-- 弃用」）、`t_scheduling`（0 行，「-- 弃用」）、`t_smart_scheduling`（算法智能排班，0 行）。选型依据是行数 + 更新时间 + 官方弃用标注三者一致。

### 明细还是聚合

**是明细。** 2026-08 一个整月，LKUS `status=1` 的排班行按 (员工, 日期) 分组：

```sql
SELECT n_rows_per_emp_day, COUNT(*) emp_days FROM (
  SELECT emp_no, scheduling_date, COUNT(*) n_rows_per_emp_day
  FROM luckyus_opempefficiency.t_emp_scheduling
  WHERE tenant='LKUS' AND status=1 AND scheduling_date>='2026-08-01' AND scheduling_date<'2026-09-01'
  GROUP BY emp_no, scheduling_date) t
GROUP BY n_rows_per_emp_day ORDER BY n_rows_per_emp_day;
```
| n_rows_per_emp_day | emp_days |
|---|---|
| 1 | **2,861** |
| 2 | **62** |

**一人一天最多 2 条**，占 2.1%。这 62 个人天的 124 行构成：`source_Type='scheduling'` 120 行、`working_time_apply`(培训 work_type=4) 2 行、`working_time_apply`(会议 work_type=3) 2 行。即绝大部分"两条"是**同一天真的排了两段班**，不是脏数据。

### 起止时间是 datetime 还是班次代码

**都不是——是字符串。**字段 `scheduling_times`，注释「排班时段，开始HH:mm~结束HH:mm，多个排班时段逗号隔开」，类型 `varchar(1000)`。配套 `rest_times` 同格式，`effect_minutes`(int，排除休息的分钟数)、`effect_hours`(float)。

### 字符串是否可靠解析

最近 12 个月 `status=1` 的 **35,754 行，35,754 行符合 `^(HH:mm~HH:mm)(,HH:mm~HH:mm)*$`，0 行为空**：

```sql
SELECT SUM(scheduling_times IS NULL OR scheduling_times='') AS empty_times,
 SUM(scheduling_times REGEXP '^([0-9]{2}:[0-9]{2}~[0-9]{2}:[0-9]{2})(,[0-9]{2}:[0-9]{2}~[0-9]{2}:[0-9]{2})*$') AS well_formed,
 COUNT(*) total
FROM luckyus_opempefficiency.t_emp_scheduling
WHERE tenant='LKUS' AND status=1 AND scheduling_date>='2025-09-01';
-- empty_times=0, well_formed=35754, total=35754
```

多段情况稀少：`scheduling_times` 含逗号的 **26 行**、`rest_times` 含逗号 **12 行**、无休息时段 **2,419 行**（占 6.8%，是短班次）。

> **补充说明（一处已知不可用字段）**：`scheduling_slot` / `scheduling_slot_result` 两个 48 位点阵字段虽存在，但不能作为排班时段的来源——需求方若看到这两个字段名不要误用。本次未对这两列做全量取值统计，判定依据是它们与 `scheduling_times` 语义重复且 `scheduling_times` 已 100% 规范。

### 对看板的影响与建议

- **可以算迟到/早退**，但 ETL 必须做一步「字符串 → `(date, HH:mm)` → 结合门店时区 → 绝对时刻」的解析。
- 建议在数据层落一张 `dim_shift`（一员工一天一班次一行，含 `scheduled_start_ts` / `scheduled_end_ts` / `scheduled_break_minutes`），把字符串解析一次性做掉，下游不再碰原始串。
- 一天两班次占 2.1%，**指标定义必须先声明是"按班次"还是"按人天"**（与 F-07 同一个决策）。

### 能不能重算？能，而且是 100%

用 `scheduling_period`（排班时段，本地 `HH:mm`）与 `clock_in_period`（打卡时段，本地 `HH:mm:ss`）两个字符串，对 2026-08 的 1,076 条 `except_type=1` 记录做拆分：

```sql
SELECT SUM(late_sec>0 AND early_sec<=0) late_only, SUM(late_sec<=0 AND early_sec>0) early_only,
       SUM(late_sec>0 AND early_sec>0) late_and_early, SUM(late_sec<=0 AND early_sec<=0) neither, COUNT(*) n
FROM (SELECT TIMESTAMPDIFF(SECOND, STR_TO_DATE(SUBSTRING_INDEX(scheduling_period,'~',1),'%H:%i'),
                                   STR_TO_DATE(SUBSTRING_INDEX(clock_in_period,'~',1),'%H:%i:%s')) late_sec,
             TIMESTAMPDIFF(SECOND, STR_TO_DATE(SUBSTRING_INDEX(clock_in_period,'~',-1),'%H:%i:%s'),
                                   STR_TO_DATE(SUBSTRING_INDEX(scheduling_period,'~',-1),'%H:%i')) early_sec
      FROM luckyus_opempefficiency.t_attendance_shift
      WHERE tenant='LKUS' AND attendance_date>='2026-08-01' AND attendance_date<'2026-09-01'
        AND except_type=1 AND scheduling_period LIKE '%~%' AND clock_in_period LIKE '_%~_%') t;
```

| late_only | early_only | late_and_early | **neither** | n |
|---|---|---|---|---|
| 638 | 311 | 127 | **0** | 1,076 |

**neither = 0，即 1,076 条全部能明确归入迟到 / 早退 / 两者兼有。**

而且 `except_type=1` 的 1,076 条中，多段排班或单边打卡的 **各为 0 条**（`multi_segment=0`, `one_sided_or_empty=0`），不存在解析不了的边缘情况。

### 🔴 一个必须写进 ETL 规范的坑：按分钟算会错 15%

同一份数据，把 `TIMESTAMPDIFF(SECOND,...)` 换成 `TIMESTAMPDIFF(MINUTE,...)`：

| 粒度 | late_only | early_only | late_and_early | neither |
|---|---|---|---|---|
| **按秒** | 638 | 311 | 127 | **0** |
| 按分钟 | 504 | 314 | 97 | **161** |

按分钟会凭空出现 161 条（15.0%）"既不迟到也不早退却被标了异常"的假矛盾——因为 `TIMESTAMPDIFF(MINUTE, '06:00:00', '05:59:37')` 向零截断成 0。**重算必须用秒。**

### iAdmin 用的容忍阈值 = 0

对照组：2026-08 的 1,561 条 `except_type=0`（正常）记录，按秒重算：

```
any_late = 0, any_early = 0, max_late_sec = 0, max_early_sec = 0, n = 1561
```

**1,561 条正常记录里，迟到秒数和早退秒数的最大值都是 0。** 说明 iAdmin 的判定是**零容忍、精确到秒**：晚 1 秒即判迟到。这解释了为什么迟到早退占了全部异常的 **73.9%**（`attendance_status=0` 共 **20,580** 条，其中 `except_type=1` 共 **15,212** 条）——在 2,637 条有排班有打卡的 2026-08 记录里，1,076 条（**40.8%**）被判异常。

### 对看板的影响与建议

1. **不能直接用 `except_type` 出六分类**，必须在数据层建一层重算：
   - Late Arrival = `first_punch_ts > scheduled_start_ts`
   - Early Departure = `last_punch_ts < scheduled_end_ts`
   - Missing Clock-In / Clock-Out = 从 `t_clock_in.punch_type` 判断 1/2 是否缺失（见 F-03 的实测分布）
   - Absence = `except_type=2`
   - Unscheduled Clock-In = `except_type=4`
2. **强烈建议同时保留 iAdmin 原判（`except_type`）作为对账列**，看板上给一个"与 iAdmin 判定不一致的记录数"监控项。两套口径并存时，业务方追问"为什么看板和 iAdmin 数字对不上"必须有据可查。
3. **需求方必须先确认容忍阈值**：零容忍会让"迟到率"长期停在 40% 量级，这个数字作为管理指标是否可用，是业务决策不是技术决策（见 `05_阻塞项与需求方问题.md` Q1）。

无 NULL、无负值、无超 24 小时。

### 抽样验证：它是怎么算出来的

对 2026-08 有完整打卡的 2,697 条班次，把 `effective_hours` 分别与两种口径比对：

```
n = 2,697
匹配「实际打卡跨度 − 实际休息打卡时长」：2,490  (92.3%)
匹配「实际打卡跨度」（无休息）：        438
两者都不匹配：                          204  (7.6%)
```

而如果改用**排班里的计划休息时长**去减，只有 1,334/2,188 = 61% 匹配。

**结论：`effective_hours` = (实际下班卡 − 实际上班卡) − (实际休息结束 − 实际休息开始)，用的是实际打卡，不是计划休息。** 无薪休息**已被扣除**。

具体一条可验算的样本（emp_h `24a9860c`，2026-08-11）：
- 排班 `06:00~13:30`，计划休息 `10:00~10:45`
- 打卡 `05:59:37~13:31:28`（跨度 7h31m52s），实际休息 `13:00:00~13:45:35` UTC = `09:00~09:45` EDT（45m35s）
- `effective_hours = 6.79`，而 7.53h − 0.76h = **6.77h**，残差 0.02h（约 1 分钟，来自打卡秒数取整）

### 一个必须知道的行为：异常班次的有效工时会被清零

| except_type | 班次数 | 其中 effective_hours=0 |
|---|---|---|
| NULL（未来占位） | 2,865 | 0 |
| 0 正常 | 17,112 | 0 |
| 1 迟到早退 | 13,820 | 86 |
| **2 旷工** | 3,595 | **3,582 (99.6%)** |
| **3 漏打卡** | 493 | **488 (99.0%)** |
| **4 未排班打卡** | 757 | **757 (100%)** |

**未排班打卡的有效工时一律记 0** —— 也就是说员工在非排班时段实际干了活，系统认定有效工时为零。这是个必须让业务方知晓的口径：**"Valid Working Hours" 不等于 "实际在岗时长"**。

### 对看板的影响与建议

- ✅ **可直接取 `effective_hours`**，不必自己配对打卡，省掉一大块 ETL。
- ⚠️ 但必须在看板上明确标注：有效工时 = 排班内的有效在岗时长，**不含未排班时段的工作、不含漏打卡当天的工作**。12.7%（4,913/38,642）的班次有效工时为 0，直接对人均工时做平均会显著低估。
- 建议同时暴露一个"实际在岗时长"（自行按打卡重算，不清零）作为对照列，供业务方判断是否要换口径（见 `05` Q2）。

**结论：🟢 可实现。`Closure Duration During Business Hours` 不但能算，而且系统已经替你算好了两遍。**

### `Closure Duration During Business Hours` 怎么算 —— 两条路，选第二条

**路径一（不推荐）**：`t_shop_focus_operation_log.closed_duration`，字段注释就是「营业时段内闭店时长（分）」，系统已算好。

**为什么不推荐**：它把跨天闭店的**全部**时长记在**开始那一天**。实测：

| 闭店 id | 门店 | 原因 | start_time (UTC) | end_time (UTC) | closed_duration | 实际跨天数 |
|---|---|---|---|---|---|---|
| 1200 | 20032 | Goverment inspection | 2026-04-02 17:50 | 2026-04-20 11:00 | **14,709 分** | 18 天 |
| 1220 | 1127 | Under renovation | 2026-05-17 04:00 | 2026-05-31 04:00 | **10,920 分** | 14 天 |
| 1198 | 20027 | In-store equipment malfunction. | 2026-03-30 16:40 | 2026-04-05 10:59 | 4,699 分 | 6 天 |

按开始日汇总会得到荒谬结果：门店 20011 在 2026-08-15 的 `SUM(closed_duration)=990 分`，而当天名义营业窗口只有 690 分。

**路径二（推荐）**：`t_shop_opening_time` 的 `nominal_minutes − business_duration`。

`business_duration`（注释「当日实际营业时长（分）」）**已经是扣除营业时段内强制闭店后的净值**，且**已正确按天拆分**。2026-08 的 744 个 LKUS 店日：

```
名义窗口 = business_duration 的：696 天（无闭店）
business_duration < 名义窗口的：  48 天（有闭店）
business_duration > 名义窗口的：   0 天
总缺口：47,814 分
```

逐条对得上：

| dept_id | date | 营业窗口 | business_duration | 名义分钟 | 当日 SUM(closed_duration) |
|---|---|---|---|---|---|
| 20029 | 2026-08-01 | 07:00–19:00 | 714 | 720 | 5 |
| 20032 | 2026-08-01 | 07:00–20:00 | 770 | 780 | 9 |
| 20016 | 2026-08-02 | 07:00–19:00 | 360 | 720 | 359 |
| 20019 | 2026-08-10 | 07:00–19:00 | **11** | 720 | 708 |
| 20011 | **2026-08-16** | 08:00–19:30 | 389 | 690 | **NULL** ← 当天没有闭店"开始"，缺口来自 08-15 起的跨天闭店 |

最后一行是关键证据：**只有 `t_shop_opening_time` 正确地把跨天闭店摊到了 08-16 这一天。**

### 对看板的影响与建议

- ✅ `Closure Duration During Business Hours` **可实现**。
- 🔴 **务必用 `nominal_minutes − business_duration`，不要 `SUM(closed_duration) GROUP BY DATE(start_time)`。** 后者在 24% 的闭店（跨天，见 F-10）上会错到离谱。
- `closed_duration` 保留作为「单次闭店事件时长」用于闭店明细列表，不用于日聚合。
- 需求方需确认 `is_business=2`（不营业日）在 LKUS 一条都没有——即系统里没有"计划歇业日"的记录（见 `05` Q4）。

### 能支持到什么刷新频率

| 频率 | 可行性 | 说明 |
|---|---|---|
| **T+1（每日）** | ✅ **推荐** | 源系统本身就是日切结算（`lag=1` 占修改量的 90%）；`t_shop_opening_time.update_time` 恒为 04:01 UTC = 00:01 EDT。**T+1 与源系统天然对齐。** |
| **小时级** | ✅ 技术可行 | 每小时全表拉 21 万行对 db.t4g.micro 有压力但可承受；建议改为「近 30 天窗口 + 每日一次全量」 |
| **准实时** | ⚠️ 不建议 | `t_attendance` 的异常判定本身是日切批处理产出的，准实时拉到的是半成品；且 `opempefficiency` 是 **db.t4g.micro**（最小规格），高频扫表有 EBS 积分耗尽风险 |

**增量还是全量：建议"全量 + 增量"混合**
- `t_shop_info` / `t_ehr_post` / `t_ehr_employee` / `t_shop_focus_operation_log` / `t_shop_opening_time`（LKUS 6,185 行）：**全量重拉**，简单可靠。

### 对看板的影响与建议

1. **看板数据集的白名单原则**：只引入 `emp_no`（或其代理键）、`post_code`、`property`、`dept_id`、日期、时长、枚举码。**上述所有列一律不进数据层。**
2. **姓名的处理**：看板若必须显示人名（如"迟到 Top 10 员工"），建议在展示层通过 API 按需查询 + 行级权限控制，**不要把 `name` 落进宽表**。
3. 🔴 **`features`（人脸特征码）、`photo_url`、`clock_pic` 绝对不能进数据管道** —— 生物识别数据的合规成本远超看板价值。
4. **行级权限**的技术基础已具备：`luckyus_ipermission.t_permission_post_dept_relation`（岗位关联部门权限，19 行）+ `t_permission_post_role_relation`（岗位关联角色，26 行）。可按"岗位 → 可见门店"实现 Store Manager 只看自己店。
5. **导出脱敏**：任何 CSV/Excel 导出必须走同一套脱敏规则，不能只在页面上遮蔽。
