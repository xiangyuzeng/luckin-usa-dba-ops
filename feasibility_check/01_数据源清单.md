## 2. 能连上的数据源

### 2.1 主通道：mcp-db-gateway（SSE）

| 项 | 值 |
|---|---|
| 端点 | `http://10.238.3.43:8080/sse`（内网，无需凭据落盘） |
| 可见 MySQL 实例 | **64 台**，命名 `aws-luckyus-{service}-rw` |
| 可见 PostgreSQL | 1 台（`aws-luckyus-pgilkmap-rw`，地图服务，与本需求无关） |
| 读写属性 | **网关强制只读**。放行 `SELECT`/`SHOW`/`DESCRIBE`/`EXPLAIN`；`SET SESSION` 被拒（`Permission denied for operation`） |
| 已知限制 | ① 每个 `aws-luckyus-{svc}-rw` 是**独立 RDS 实例**，跨库 JOIN 不可用，必须分实例取数后在应用层拼；② SELECT 中出现 `REPLACE(...)` 会被写关键字守卫误杀（本次已实测触发一次，见 `04_evidence.sql` F-01 段的 `[ERROR]` 记录）；③ `group_concat_max_len=1024` 不可调 |

### 2.3 每个数据源能看到的库（本次扫描命中的）

对全部 64 台跑同一条 `information_schema.TABLES` 模式扫描，**40 台有命中**。与本需求相关的前 8 台：

| 服务器 | 库 | 命中表数 | 说明 |
|---|---|---|---|
| `aws-luckyus-opempefficiency-rw` | `luckyus_opempefficiency` | 26 | 考勤/打卡/排班/门店员工，本需求核心 |
| `aws-luckyus-iehr-rw` | `luckyus_iehr` | 43 | 员工主数据、岗位、请假、异动、离职 |
| `aws-luckyus-opshop-rw` | `luckyus_opshop` | 15 | 门店主数据、营业时间、闭店、无人打卡 |
| `aws-luckyus-opshopsale-rw` | `luckyus_opshopsale` | 19 | 售卖方案，与本需求无关 |
| `aws-luckyus-iadmin-rw` | `luckyus_iadmin` | 14 | **全部是审批流引擎表**（`t_approval_*`），**不含任何考勤/排班/门店数据** |
| `aws-luckyus-ibehr-rw` | `luckyus_ibehr` | 11 | 表结构与 iEHR 同名，但**全部 0 行**，未启用 |
| `aws-luckyus-ipermission-rw` | `luckyus_ipermission` | 4 | 岗位-角色/部门权限关联，行级权限设计时需要 |
| `aws-luckyus-pubdm-rw` | `luckyus_pub_dm` | 4 | 门店信息副本（MQ 同步），非权威源 |

> **关键结论：「iAdmin」不是一个库。**
> `luckyus_iadmin` 库里只有审批流引擎表（`t_approval_define` / `t_approval_instance` / `t_approval_task` 等 14 张，见 `04_evidence.sql` 第 0 段）。需求文档里 "Operations System → Working Hours → ..." 这些菜单路径背后的数据**分布在 `opempefficiency`、`opshop`、`iehr` 三个独立 RDS 实例上**。这直接决定了：**看板取数必然是跨实例的，不存在一条 SQL 出全部指标的可能，必须先落到统一的数据层。**

### 2.4 只读副本情况

`aws rds describe-db-instances` 返回的 78 个实例中，**`ReadReplicaSourceDBInstanceIdentifier` 全部为 `null`——整个机队没有任何只读副本**。

因此"优先连只读从库"这一约束在本环境下**无从满足**：唯一可用通道是主库端点，但由 mcp-db-gateway 强制降级为只读。本次所有业务表查询均带时间范围过滤或 `LIMIT`，未做无条件全表扫描；三张核心事实表最大也只有 12.7 万行，单次扫描代价可忽略。
