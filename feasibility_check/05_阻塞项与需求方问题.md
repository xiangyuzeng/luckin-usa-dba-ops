## 🔴 P0 —— 不答就无法开工的三条

### Q1｜迟到 / 早退的容忍阈值是多少分钟？

**问谁**：Operations / OM 团队（指标定义方），需 HR 会签

**已查到的事实**
- iAdmin 当前用的是**零容忍、精确到秒**：2026-08 的 1,561 条判定为"正常"的班次里，迟到秒数和早退秒数的最大值**都是 0**（F-02）。晚 1 秒即判迟到。
- 结果是 2026-08 有排班有打卡的 2,637 条记录中，1,076 条（**40.8%**）被判为迟到早退；迟到早退占全部考勤异常的 **74%**。
- 拆开看：纯迟到 638、纯早退 311、两者兼有 127。
- 容忍阈值的敏感度（2026-08，按秒计）：

| 容忍阈值 | 迟到条数 | 早退条数 |
|---|---|---|
| **0 秒（当前）** | **765** | **438** |
| 1 分钟 | 601 (−21%) | 411 (−6%) |
| 5 分钟 | 381 (−50%) | 354 (−19%) |

**为什么必须先答**
这个阈值直接决定看板首页最大那个数字。40% 的迟到率作为管理指标，要么说明确实有普遍问题、要么说明阈值不合理 —— 但这不是 DBA 能判断的。而且阈值一变，历史数据要全部重算，看板上线后再改会导致所有历史趋势断裂。

**不答的后果**
只能沿用 iAdmin 的零容忍口径。看板上线第一天就会显示"迟到率 40%"，大概率立刻被质疑，然后返工重算全部历史。

### Q2｜"Valid Working Hours" 要不要包含未排班时段实际干的活？

**问谁**：Operations / OM 团队，需 HR 与 Finance 会签（涉及工时口径与薪资）

**已查到的事实**
- 系统现成的 `effective_hours` 字段在下列情况**一律记 0**（F-03）：
  - `except_type=4` 未排班打卡：**757 / 757 条全部为 0（100%）**
  - `except_type=2` 旷工：3,582 / 3,595（99.6%）
  - `except_type=3` 漏打卡：488 / 493（99.0%）
- 合计 **12.7%（4,913 / 38,642）** 的班次有效工时为 0。
- 也就是说：**员工在非排班时段实际到店干了活，系统认定其有效工时为零。**
- `effective_hours` 的算法已验证：= (实际下班卡 − 实际上班卡) − (实际休息结束 − 实际休息开始)，92.3% 可复现，无薪休息已扣除。

**为什么必须先答**
决定两件事：① 是直接取现成的 `effective_hours`（省一大块 ETL），还是自己按打卡重算"实际在岗时长"；② 人均工时这个指标的分母怎么定 —— 把 12.7% 的 0 值算进平均数，会显著低估。

**不答的后果**
若默认取 `effective_hours`，"人均有效工时"会比实际在岗时长系统性偏低，而 Ops 看到的"排班工时 vs 有效工时"缺口里会混进大量本该算工时的劳动。这在美国劳动法语境下不是小事。

### Q3｜LKUS 门店员工的请假实际走什么流程？

**问谁**：HR（HR Head / HRBP）

**已查到的事实**
- iEHR 的请假模块表结构完整、字典齐全（9 类：annual / sick / unpaid / maternity / compassionate / juryDuty / electionDay / fmla / nationalReserve）。
- 但 **LKUS 的请假单只有 7 条，且全部是 `status=2`（审批取消）。已批准（`status=1`）的条数 = 0**（F-09）。
- 两条独立路径交叉验证：`t_attendance.type=5`（请假）在 41,798 行里只有 **1 行**；`t_emp_scheduling.source_Type='ehrLeave'` 也只有 **1 行**。
- 同期 IQA2（测试租户）有 7 条已批准 —— 说明功能是通的，只是 LKUS 没在用。

**为什么必须先答**
需求要求"判定 Absence 时排除已批准请假"。数据源是空的，这条规则**现在无法实现**。需要知道请假到底记在哪里（Lark 审批？线下表单？店长口头？），才能决定是接新数据源、还是改指标定义。

**不答的后果**
🔴 **Absence 指标会把请假的人算成旷工。** 现有 3,881 条 `except_type=2` 里混了多少已批准请假，数据无法回答。看板一旦按"旷工"展示并用于绩效，就是对一线员工的错误归因 —— 这是劳资纠纷和合规风险，不只是数字不准。
最低限度的兜底：Absence 指标必须改名并显式标注口径为 **"No Clock-In Without Schedule Change"**（未打卡且未办理排班变更），不能叫 Absence / 旷工。

## 🟠 P1 —— 影响模块范围的四条

### Q4｜"营业时段内闭店时长" 的分母怎么定？门店有没有计划歇业日？

**问谁**：Operations 团队

**已查到的事实**
- `t_shop_opening_time.is_business=2`（不营业）在 LKUS **6,185 行里一条都没有** —— 系统里不存在"计划歇业日"的记录（F-04）。
- 节假日机制存在（`t_shop_opening_plan` 的 `date_type=0` 特殊日期）但**LKUS 全库只有 1 条**，覆盖 1 家门店 1 天（2026-09-24）。
- 全机队 64 台按 `holiday|vacation` 表名模式扫描：**无任何节假日字典表**。
- 25 家 `status=1` 门店中，2026-08 完全没有营业时间数据的有 **1 家**。

**为什么必须先答**
"闭店时长占比"的分母是"应营业总时长"。如果实际上有节假日歇业但没记进系统，分母会偏大、闭店占比偏小。

**不答的后果**
按现有数据算出来的分母 = 每天都应该营业。感恩节、圣诞节等实际歇业日会被算成"应营业但未营业"，或者反过来被计入正常营业时长。

### Q5｜C 模块统计范围：只算无人打卡导致的闭店，还是全部强制闭店？另外 "Emergency Closure" 在 iAdmin 界面上是哪个控件？

**问谁**：Operations 团队（需求提出方）

**已查到的事实（范围问题）**
| 口径 | 近 12 个月次数 | 近 12 个月总时长 |
|---|---|---|
| 仅无人打卡自动强闭（`reason_id = -1`） | **84** | **2,795 分钟** |
| 全部强制闭店（`operation_scene = 1`） | **168** | **53,318 分钟** |

**两者相差 2 倍次数、19.1 倍时长。**

- 无人打卡记录（`t_nobody_focus_closed_log.type=2`，88 条）与闭店日志的 `reason_id=-1` 记录**可按 门店+日期 100% 匹配（88/88）**，两个口径之间可以自由换算。
- 无人打卡是两级机制：UTC 10:00（EDT 06:00）预警 → 10 分钟后 UTC 10:10 自动强闭。预警 482 次里只有 88 次升级（18.3%）。
- 🔴 值得单独提醒：无人打卡强闭在 **2026-08 突增到 31 次**（前 12 个月月均 4.6 次），2026-09 前 9 天已 11 次。

**已查到的事实（Emergency Closure 问题）**
- `luckyus_opshop` 全库**没有任何字段名或字段注释含 emergency / urgent / 紧急 / 应急**（`information_schema.COLUMNS` 全库扫描，命中 0）。
- LKUS 的 12 条闭店原因字典里**没有叫 "Emergency Closure" 的**：One staff working / Landlord's issue / Under renovation / School holiday break / License issue / In-store equipment malfunction. / Food safety issue / Internet interruption / Goverment inspection / Weather issue / Water and power outage。
- 唯一带"紧急"字样的是**另一个库**的 `luckyus_opshopsale.t_temp_sale`（按商品紧急停售），是**商品级停售不是门店闭店**，语义不同不能替代。

**为什么必须先答**
范围决定 C 模块所有数字的量级；"Emergency Closure" 若是需求方看到的某个 UI 标签，需要指出它对应界面上的哪个位置，才能反查是哪个字段/枚举。

**不答的后果**
C 模块的数字可能整体差 18 倍；"Emergency Closure" 相关指标只能标注为"字段不存在"并从 V1 移除。

### Q6｜`t_clock_in.type` 这个字段是什么意思？

**问谁**：iAdmin / 人效系统研发团队（China HQ 或本地研发）

**已查到的事实**
- `t_clock_in` 有两个类型字段：`punch_type`（注释完整：1上班卡 2下班卡 3休息开始 4休息结束）和 **`type`（注释只有「打卡类型」四个字，无枚举定义）**。
- LKUS 实测 `type` 只取 **3** 和 **4** 两个值，分布与 `punch_type` 交叉后没有明显规律（`type=4` 是主体 **124,149** 条，`type=3` 是 **2,667** 条）。
- `virtual_type`（虚拟打卡类型）注释里有 0/2/3 三个值，LKUS **全部为 0**。

**为什么必须先答**
本次核验的所有结论都**没有依赖 `type`** —— 但如果它区分了"设备打卡 vs 补卡"或"到店 vs 外勤"，可能影响工时口径。在写 ETL 之前需要确认它能不能被安全忽略。

**不答的后果**
按"可忽略"处理。风险可控（当前所有指标都不用它），但若日后发现它区分了打卡渠道，可能需要回溯重算。

### Q7｜岗位口径三问：Shift Leader = Shift Supervisor 吗？Trainee 算不算管理岗？`property=4` 是什么？

**问谁**：HR + Operations 团队

**已查到的事实**

*(a) Shift Leader*
- `t_ehr_post` 的 266 条 LKUS 岗位定义里**没有任何一条名称含 "Leader"**。
- 最接近的是 **`Shift Supervisor`**（post_code `LKUS00000085`，在职 **48** 人，全部全职）。

*(b) Trainee 岗*
| 岗位 | 在职 |
|---|---|
| Store Manager | 23 |
| Assistant Store Manager | 18 |
| Shift Supervisor | 48 |
| **小计（不含 Trainee）** | **89** |
| Store Manager Trainee | 4 |
| Assistant Store Manager Trainee | 1 |
| Shift Supervisor Trainee | 1 |
| **含 Trainee 合计** | **95** |

*(c) `property = 4`*
- `t_ehr_employee.property` 字段注释是「0-全职，1-兼职，2-实习，3-外包」。
- LKUS 在职员工里出现了 **`property = 4`，4 个人**，入职日期 2026-07-20 / 2026-08-03 ×2 / 2026-08-05（都是近两个月新入职），且这 4 人的 `employment_type` 与 `main_type` 都是 NULL。
- 字典里的 `2=实习` 和 `3=外包` 在 LKUS **一个人都没有**。
- 另：LKUS **没有任何兼岗记录**（`t_ehr_employee_post_relation` 全部 `relation_type=0`），一人一岗，岗位归属无歧义。

**为什么必须先答**
决定"管理岗覆盖率""管理岗人均管辖人数"之类指标的分子分母。89 vs 95 差 6.7%；`property=4` 的 4 人无法归入 FT/PT 任一类。

**不答的后果**
默认按 Shift Leader = Shift Supervisor、Trainee 不计入管理岗（分子 89）、`property=4` 单列为 "Unclassified"。需在看板上注明这三条假设。

## 🟡 P2 —— 影响维度设计与实施路径的两条

### Q8｜"按 Management Area 下钻" 还要不要做？

**问谁**：Operations 团队 + 需求提出方

**已查到的事实**
- `t_shop_info.operation_area`（运营管理区域部门编码）在 **LKUS 全部 33 家门店上都是同一个值 `LKUS00000041`** —— 只有一个区域（F-11）。
- 历史上曾有第二个区域 `LKUS00000052`，在 **2025-12-24 ~ 2026-05-16** 期间用于 **8 家门店**（dept_id 1140 / 20010 / 20016 / 20019 / 20026 / 20027 / 20031 / 20032），2026-05 之后全部并回 041。考勤表里有 **7,396 条**记录带着这个历史区域码。
- 🔴 **主数据表已被覆盖，只保留当前值。** 历史区域归属只在考勤表的 `scheduling_dept_operation_area` / `clock_in_dept_operation_area` 快照字段里留痕。
- 备选方案也不成立：`t_shop_info` 的 `administrative_area_name` / `locality_name` / `sublocality_name` 三级行政区字段在 LKUS 25 家在营门店上**全部为 NULL**。
- 全机队 64 台按表名和列名的 `area` 模式扫描，**未找到任何管理区域层级表 / 字典表**。

**为什么必须先答**
这是一个完整的看板维度。现在做出来所有门店会落进同一格，图表是一条柱子。

**不答的后果**
V1 只能砍掉这个维度，或用"门店"直接代替"区域"。若日后 Ops 补齐区域划分，历史数据的区域归属需要单独回填（且 2026-05 之前的只能从考勤快照反推）。

### Q9｜这 8 张表是不是已经同步到数仓了？能不能给 `databasecheck` 开只读权限？

**问谁**：Michael（CTO / AWS 账号 owner）或数据平台负责人

**已查到的事实**
```
aws redshift-serverless list-workgroups --region us-east-1
→ AccessDeniedException: User arn:aws:iam::257394478466:user/databasecheck is not authorized
  to perform: redshift-serverless:ListWorkgroups

aws glue get-databases --region us-east-1
→ AccessDeniedException: ... not authorized to perform: glue:GetDatabases
```
- `databasecheck` 没有 Redshift Serverless 和 Glue Data Catalog 的读权限，**无法确认数仓里是否已有这 8 张表的副本**。
- 源端已确认：三张核心事实表合计 21 万行（LKUS），日增约 646 行，`create_time` / `modify_time` 100% 非空但**都没有索引**；实测业务日期最长被回改 **18 天**。
- `aws-luckyus-opempefficiency-rw` 是 **db.t4g.micro**（最小规格），高频全表扫描有 EBS 突发积分耗尽的风险。

**为什么必须先答**
如果数仓里已经有了，看板直接接数仓；如果没有，才需要新建一条 ETL 链路。这是"要不要建"的问题，不是"怎么建"的问题。

**不答的后果**
可能重复建设一条已经存在的同步链路，并给一台 t4g.micro 实例增加不必要的负载。

**具体请求**：给 `databasecheck` 加 `redshift-serverless:ListWorkgroups` / `redshift-data:*`（只读）和 `glue:GetDatabases` / `glue:GetTables` 权限即可，不需要数据读权限。
